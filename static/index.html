PRODUCT DOCUMENTATION

Help & user guide

A practical, task-based guide to investigating legacy repositories. Everything stays local unless you explicitly export and share evidence.

1. Get started

Choose a local Git repository under Overview → Repository details and toolchain. Repo Studio reads committed HEAD. Working-tree edits are not analyzed or changed. If HEAD changes, reopen the repository to select the new commit.

Start with Run code analysis and optionally Scan duplications. These are separate operations with separate results.

2. Run analyses

Run code analysis

Reads committed Python sources using AST rules and reports import cycles, complexity candidates and conservative possibly-unused candidates. It does not execute project modules.

Scan duplications

Runs the optional jscpd tool against a committed snapshot. Reported matches are potential overlap, not a guarantee that code is safe to remove. This may take longer than the Python analysis.

Both commands show an activity state. A running indicator reflects actual pending work; there is no fabricated percentage progress.

3. Read the dashboard

The five cards summarize scanned Python files, import cycles, complexity candidates, possibly-unused eligibility, and duplication matches. Donut segments and hotspot bars open the underlying findings. N/A means not eligible; — means not yet measured.

4. Investigate dependencies

In Dependency explorer, select a detected static cycle and follow the arrow for an import to open its source location. The diagram is a focused view of detected edges, not a complete execution or dependency graph.

5. Build AI investigation context

Choose a finding, compare Compact/Balanced/Extended evidence, then use Investigation Context Builder to include or exclude source excerpts. The budget is an approximation (characters ÷ 4), not a measured tokenizer count. Exclusions and missing evidence remain disclosed in the exported Markdown.

6. Review professional findings

Open Professional findings to inspect imported diagnostics from supported Ruff, Pyright, Bandit and Vulture reports. These are observations, not confirmed defects, and the view does not automatically run the analyzers.

Use Area, Review queue and Analyzer to narrow the results; Hide labeled noise affects only the view, not the original report. Review-first and other queue labels help organize work, not establish severity. Open the committed source and verify the surrounding context before taking action.

Professional findings are not yet linked to the Investigation Workspace history shown in Dependency explorer. Do not interpret an empty history as proof that imported diagnostics were reviewed.

7. Track investigations and exports

In Dependency explorer → Investigation Context Builder, select a finding and load its evidence. Choose Progress (Pending, Reviewing, Reviewed) independently from Decision (Undecided, Keep, Investigate further, Propose change). Write notes and select Save review. These are human-entered records, not an automatic approval or fix.

Under Investigation history, use filters for review status, decision and Export history to find entries previously exported or never exported. Copy investigation and Save Markdown create user-controlled evidence exports; do not assume a note is exported merely because it was saved. Refresh history to see new records.

History is scoped to the repository and commit identity. Reopening another commit does not silently transfer conclusions or mark findings as solved.

8. Coverage and source revalidation

Evidence coverage indicates whether referenced source anchors and context are present. It is not code coverage, correctness, execution reachability, or a safety score. Missing anchors must remain visible rather than being counted as zero findings.

In Investigation history, filter Source revalidation by Changed source, Unchanged source, Not verifiable, or Current commit. These labels compare available evidence; an unchanged excerpt does not prove behavior is unchanged. Verify changed sources and relevant tests before reusing a previous decision.

9. Install, update and recover

Requirements: Python 3.10+, Git, a modern browser and a local committed Git repository. The core application needs no runtime pip dependencies. Start the portable Linux app with python3 -B studio.py --repo /absolute/path/to/repository --port 8765. In Windows, use the per-user install_windows.ps1 procedure from the extracted source package.

For full installation, update and rollback instructions read INSTALL_OMARCHY.md, INSTALL_UBUNTU.md or WINDOWS_INSTALL.md in the downloaded source package or GitHub repository. An Omarchy installation may have a separate manager; do not overwrite manager-controlled files manually.

Back up your application data and configuration before an upgrade. The Workspace database lives outside the source tree. An application-code rollback is not a guarantee of database-schema downgrade compatibility.

10. Human review & privacy

Repo Studio does not refactor, commit, push, delete or call an AI provider. The developer chooses which evidence to share. Exports may contain proprietary source code, credentials or sensitive comments: review the generated text before pasting it into any external service.

Evidence coverage describes source-anchor completeness, not correctness, safety or suitability to merge.

11. Troubleshooting

Missing duplicates? Check that jscpd is configured and run Scan duplications. Possibly unused = N/A? The analysis was ineligible; that is not evidence of no unused functions. Missing context? Check whether the Repowise index corresponds to the selected repository and commit. Long-running scan? The activity indicator remains visible while the operation is pending; some audits can take longer.

ABOUT THIS PROJECT
RS

Repo Studio

Evidence-first legacy-code investigations, with human-controlled AI workflows.

Version 0.9.9 · Local-first · Read-only

Purpose

Inspect a selected Git commit, surface maintainability candidates, navigate real code, and create focused evidence for independent AI-assisted reasoning.

Safety boundaries

No automatic refactoring, no code execution from analyzed modules, and no automatic uploading of code. Generated analysis is advisory and must be reviewed by a person.

Limitations

Static relationships can be incomplete. Unused-code heuristics may be ineligible. Token budgets are estimates until measured externally. Some analyzers and indexes are optional.

Support & documentation

See for workflows, controls, troubleshooting and illustrative screenshots. The local README documents installation and tests.
